# AI Challenge App

Минимальное full-stack приложение на Go: браузер отправляет вопрос локальному серверу, сервер вызывает DeepSeek API и возвращает текстовый ответ. Frontend написан на обычных HTML, CSS и JavaScript, поэтому проект легко показать и объяснить на видео.

## Что происходит

```text
Браузер → POST /api/chat → Go backend → DeepSeek API
Браузер ← JSON с ответом ← Go backend ← DeepSeek API
```

API-ключ не попадает в браузер: при запуске сервер сначала использует непустое значение `DEEPSEEK_API_KEY` из окружения процесса, а если его нет — значение из локального файла `.env`. Ключ передаётся DeepSeek только в HTTP-заголовке `Authorization`.

## Быстрый запуск

Требуется Go 1.25 или новее: проект использует актуальный официальный Go SDK для MCP.

1. Откройте Terminal и перейдите в папку проекта:

   ```bash
   cd /Users/artemiy/Ai_projects/ai-challenge-app
   ```

2. Создайте локальный файл конфигурации — Git его игнорирует:

   ```bash
   cp .env.example .env
   chmod 600 .env
   ```

3. Откройте `.env` локальным редактором и вставьте ключ после `=`:

   ```text
   DEEPSEEK_API_KEY=вставьте_ваш_ключ_сюда
   ```

4. Запустите приложение в том же окне Terminal:

   ```bash
   go run .
   ```

5. Откройте [http://localhost:8080](http://localhost:8080), задайте вопрос и нажмите кнопку.

Чтобы остановить сервер, нажмите `Ctrl+C` в Terminal. Для временной подмены ключа можно задать `DEEPSEEK_API_KEY` в окружении перед запуском: его непустое значение имеет приоритет над `.env`. Для другого порта перед запуском выполните `export PORT=8090`.

> Файл ключа — `.env` в корне проекта. Его имя зафиксировано в константе `localEnvFile` в [main.go](main.go), а имя строки с ключом — в `apiKeyEnvVar` того же файла. `.env.example` — безопасный шаблон; `.env` исключён из Git и содержит только локальный секрет.

## Структура

- `main.go` — HTTP-сервер, маршруты, чтение локального API-ключа и базовые защитные заголовки.
- `internal/agent/agent.go` — самостоятельный агент: системная инструкция, настройки генерации, стек сообщений и отдельные истории сессий.
- `internal/agent/store.go` — JSON-хранилище истории агента между перезапусками.
- `internal/deepseek/client.go` — Go HTTP-клиент и запрос к DeepSeek.
- `internal/handlers/handlers.go` — проверка входного JSON и понятные ошибки.
- `internal/models/models.go` — формы JSON-запросов и ответов.
- `static/` — страница, стили и JavaScript для уроков и сравнений результатов.
- `*_test.go` — автоматические тесты backend-логики.

## MCP: Яндекс Диск и GitHub

В существующий Go-сервер встроены MCP-сервер и MCP-клиент из официального
`github.com/modelcontextprotocol/go-sdk`. Они соединяются через in-memory
transport: приложение выполняет настоящий MCP handshake, запрашивает
`tools/list` и вызывает инструменты через `tools/call`, но не поднимает второй
HTTP-сайт и не запускает отдельный процесс.

Яндекс Диск MCP публикует четыре инструмента:

- `list_desktop_videos` — показывает MP4, MOV, MKV, WEBM, AVI и M4V на Рабочем столе;
- `analyze_desktop_video` — через локальный `ffprobe` читает длительность, контейнер, кодеки, разрешение и FPS, не отправляя видео модели;
- `estimate_video_upload` — показывает размер файла, свободное место на Диске и влияние на токены;
- `upload_video_to_yandex` — загружает выбранное видео в `AI Challenge/lession N` после явного `confirm=true`.

Для реальной загрузки добавьте в локальный `.env`:

```text
YANDEX_DISK_OAUTH_TOKEN=ваш_oauth_токен
YANDEX_DISK_ROOT=AI Challenge
```

По умолчанию видео ищутся в `~/Desktop`. Для тестовой или другой папки можно
задать `VIDEO_SOURCE_DIR=/абсолютный/путь`. После `go run .` внизу страницы
виден общий каталог подключённых MCP-серверов, их инструментов и журнал
`tools/list`; отдельного учебного блока Яндекс Диска в интерфейсе нет.
Ручной формы загрузки нет: напишите в основном чате «Загрузи последнее видео с
Рабочего стола в папку lession 16». Агент получает живые схемы MCP, вызывает
`list_desktop_videos`, использует точное имя найденного файла и просит явное
подтверждение. После ответа «Подтверждаю, загружай» он вызывает
`upload_video_to_yandex`. Выполненные MCP-вызовы видны в техническом журнале
чата. Без OAuth-токена список инструментов работает, а загрузка заблокирована.

Примеры естественных команд: «Какие видео есть на Рабочем столе?», «Найди
последнюю запись», «Проанализируй последнее видео», «Какое у него разрешение и
FPS?», «Сколько места оно займёт?», «Поместится ли оно на Яндекс Диск?» и
«Загрузи последнее видео в папку lession 16».

Видео не кодируется в JSON и не передаётся модели: Go-сервер получает временный
upload URL через REST API Яндекс Диска, затем потоково отправляет файл напрямую.
Поэтому размер видео расходует место на Диске и сетевой трафик, но не превращается
в токены. DeepSeek получает только текст схем инструментов, аргументы и компактные
JSON-результаты. Сервер дополнительно сверяет имя перед загрузкой со свежим
результатом `list_desktop_videos`, поэтому модель не может загрузить выдуманный
путь, и принудительно требует отдельное подтверждение внешней записи.

Перед загрузкой инструмент запрашивает общую и занятую квоту Яндекс Диска и
показывает, помещается ли файл. Одна загрузка выполняет два HTTP-запроса к API:
получение upload URL и отправку файла. Условия объёма определяются вашим тарифом
Яндекс Диска; отдельной посекундной тарификации MCP или токенов за байты видео нет.

GitHub MCP использует GitHub REST API и также подключён к агенту через
in-memory MCP transport. Он регистрирует четыре инструмента:

- `github_get_repository` — сведения о подключённом репозитории и его ветке по умолчанию;
- `github_list_files` — структура файлов и папок выбранной ветки;
- `github_get_file` — чтение UTF-8 текста файла по пути и опциональной ветке;
- `github_list_issues` — список issues;
- `github_put_file` — создание или обновление текстового файла отдельным коммитом.
- `github_delete_file` — удаление текстового файла отдельным коммитом после явного подтверждения.

По умолчанию выбран `Desuzed/ai-challenge-app`; его можно заменить локальной
настройкой `GITHUB_REPOSITORY=owner/repository`. Чтение публичных данных не
требует секретов. Для записи добавьте в `.env` fine-grained
`GITHUB_TOKEN` с правом **Contents: Read and write**. Инструмент записи и агент
требуют явное подтверждение пользователя, поэтому коммит не создаётся от одного
неподтверждённого запроса. Например, можно спросить «Какая ветка по умолчанию у
GitHub-репозитория?» или «Прочитай README.md из GitHub». Ответ использует
фактический результат MCP-вызова; вызовы отображаются в журнале чата.

## День 13: состояние задачи как конечный автомат

Под чатом находится дашборд **«План проекта»**. Чтобы начать планирование, пользователь отправляет в обычный чат сообщение со строками `Цель:`, `Этапы:` и `Шаг:`. Агент-проектировщик автоматически создаёт сохранённый план и возвращает JSON с читабельным ответом и данными дашборда: подробным текстовым ТЗ, текущим шагом, ожидаемым действием, открытыми вопросами, решениями, следующими шагами и расходом токенов.

Жизненный цикл задачи контролирует сервер, а модель лишь готовит содержание текущего этапа. Допустима только последовательность `planning → execution → validation → done`: кнопка **«Утвердить план»** открывает реализацию, **«Реализация готова»** — валидацию, а **«Валидация успешна»** завершает задачу. **«Вернуться к доработке»** отводит на один предыдущий этап и сбрасывает подтверждения всех следующих этапов. Прямое переключение этапа, завершение без проверки и предложение модели изменить `phase` отклоняются; в дашборде видны три серверных подтверждения переходов. На любом незавершённом этапе доступна пауза; она прерывает текущий запрос к модели на сервере, фиксирует сообщение «Задача приостановлена» и сохраняет остановленную команду. После «Продолжить» эта команда автоматически запускается снова с сохранённым планом. Агент проектирует только текстовое ТЗ и не реализует продукт или код.

«Текстовое ТЗ» — рабочая версия плана, которую агент обновляет по ходу обсуждения. Когда агент переводит проект на последний этап, а открытых пунктов уже нет, проектировщик автоматически создаёт самостоятельный Markdown-артефакт. Он сохраняется в разделе **«Итоговый артефакт»** вместе с названием и доступен для копирования; последующие обычные сообщения его не перезаписывают.

Кнопка **«Параметры»** объединяет технические параметры чата, профили агента и слои памяти.

## День 12: персонализация поверх памяти

Под чатом появился каталог **профилей агента**. У профиля есть произвольное название, роль или контекст, стиль, формат и ограничения. Это универсальный механизм: профиль может описывать экспертную роль, аудиторию, тип задачи или способ работы. «Химик», «Психолог» и «Экономист» — только примеры.

Профили не смешиваются с памятью: память хранит факты, а профиль задаёт роль или контекст ответа. Каталог принадлежит пользователю и доступен в его сессиях; в каждой сессии выбирается собственный активный профиль. После выбора агент автоматически добавляет отдельный системный блок активного профиля в **каждый** запрос этой сессии. В блоке «Последний запрос к модели» это видно по полю `Профиль: применён автоматически`, а в «Логах» — по полному отправленному контексту.

Проверка: создайте «Химика» и «Психолога», задайте им разные перспективы, по очереди выбирайте их и отправляйте один вопрос: «Напиши пост о кофеине». В логах будут разные system-блоки профилей, а ответы должны отличаться научной и психологической оптикой. Автотесты проверяют, что два профиля создают разные контексты модели, что активный профиль выбирается отдельно для двух сессий и что глобальная память видна в другой сессии того же пользователя.

Кнопка «Удалить всю историю» по-прежнему начинает новую задачу: краткосрочный диалог и рабочая память очищаются, но каталог профилей и активный профиль сохраняются. Профиль можно отключить через «Без профиля» или удалить из каталога.

## День 11: явная модель памяти агента

В чате одновременно работают три отдельные памяти. Их содержимое видно под полем ввода и возвращается API в объекте `memory`; это позволяет проверить не только ответ, но и данные, повлиявшие на него.

1. **Краткосрочная (`short_term`)** — последние `N` реплик текущего диалога. Она заполняется только сообщениями пользователя и ответами агента, а при скользящем окне ранние реплики не уходят в модель.
2. **Рабочая (`working`)** — факты текущей задачи: цель, дедлайн, артефакты, ограничения. У каждой реплики есть кнопка «В рабочую»: она сохраняет весь текст сообщения без ручного ключа; агент не делает таких записей автоматически.
3. **Долговременная (`long_term`)** — глобальные факты пользователя в категориях `decisions` и `knowledge`. Она не привязана ни к сессии, ни к выбранному профилю: факт, сохранённый в одном диалоге, доступен в другом диалоге того же пользователя. Сервер сам создаёт технический ключ, а весь текст сохраняется целиком.

Перед следующим вызовом модели агент добавляет отдельные системные блоки активного профиля, глобальной долговременной памяти, рабочей памяти, после чего — краткосрочное окно диалога. Записи памяти помечены как данные, а не как инструкции. Поэтому можно проверить эффект: сохраните в рабочую память `task: экран заказа`, в долгосрочную — `knowledge.language: Русский`, затем спросите «Что учесть?». В журнале ответа и в тесте видно, что обе записи попали в запрос, а короткая история осталась ограниченной `N` репликами.

После каждого успешного ответа блок **«Последний запрос к модели»** показывает фактические входные и выходные токены из `usage`, сумму и признак, были ли в конкретный запрос переданы рабочая и долговременная память. Так можно честно сопоставить ответ, цену контекста и факт передачи памяти модели.

В `.local/agent-history.json` сессии и пользователи лежат отдельно: у сессии — `messages`, `workingMemory` и `activeProfileId`, у пользователя — `profiles` и глобальная `longTermMemory`. Автоматический `Sticky Facts` ниже сохранён как прежний учебный режим сравнения контекста.

Кнопка **«Удалить всю историю»** начинает новую задачу: она очищает краткосрочный диалог и рабочую память, но сохраняет глобальные решения и знания. Их можно удалить по одной записи или отдельной кнопкой **«Очистить глобальную долговременную память»**.

В окне **«Параметры»** доступен выбор модели для текущего чата. Браузер читает `GET /api/agent/models`, а сервер передаёт только модели, одновременно доступные ключу DeepSeek и поддержанные агентом: `deepseek-flash` и `deepseek-v4-pro`. Выбор сохраняется в сессии и отправляется с каждым сообщением; ключ API в ответах и браузере не появляется.

## День 10: три стратегии контекста без summary

В чате есть переключатель, который выбирает одну из трёх стратегий. Значение `N` — от 2 до 40 сообщений. Вызова модели для сжатия нет.

1. **Sliding Window** хранит и отправляет только последние `N` реплик: всё раньше удаляется.
2. **Sticky Facts / Key-Value Memory** после каждого сообщения пользователя локально обновляет отдельный набор `key → value` (`goal`, `constraints`, `preferences`, `decisions`, `agreements`, `latest_request`). В модель уходят этот явно видимый блок и последние `N` реплик. Экстрактор намеренно детерминированный — он не создаёт скрытого summary и не расходует второй LLM-вызов.
3. **Branching** хранит независимые ветки. В режиме веток создайте checkpoint, затем две ветки от него; сообщения в одной ветке не меняют другую. Нажатие на ветку делает её активной.

Состояние сессии в `.local/agent-history.json` содержит выбранную стратегию, facts, checkpoint’ы и ветки, поэтому сохраняется после перезапуска. Старый JSON с простым массивом реплик читается как история Sliding Window.

Перед кнопкой **«Запустить 3 прогона»** раскрыт полный исходный учебный диалог: общий system prompt, все 15 реплик, KV-блок facts и правило, какие реплики попадут в каждый режим. Он загружается read-only через `GET /api/agent/strategy-demo` и не вызывает модель. Учебный прогон использует текущее значение `N` в форме: оно применяется к Sliding Window и Facts; Branching всегда передаёт всю активную ветку. Кнопка делает три реальных вызова модели для того же сценария о функции отслеживания заказа для Android и iOS. В карточках есть каждый ответ, фактические входные/выходные токены и точный отправленный контекст. Для сравнения: оцените полноту ТЗ (качество), сохранение ранних требований при следующем вопросе (стабильность), входные токены (расход) и понятность операций с памятью (удобство). Обычно Sliding Window дешевле, но теряет ранние детали; Facts удерживает явные договорённости при компактном контексте; Branching наиболее прозрачно сохраняет независимые сценарии, но несёт полную историю активной ветки.

Ниже находится **интерактивная лаборатория Branching**. Она загружает отдельную общую историю без вызова модели. Нажмите «Создать checkpoint», последовательно откройте Android- и iOS-ветку, затем запустите сравнение. `POST /api/agent/branching-demo` выполнит два независимых вызова: в каждом окажутся общий checkpoint и только продолжение соответствующей ветки. Карточки показывают оба ответа, точные input/output tokens и суммарный расход; общий checkpoint повторяется в двух запросах, что наглядно показывает цену изоляции веток.

## День 8: токены в диалоговом агенте

Главная часть страницы — простой чат с агентом. Вкладка для него не нужна: предыдущие уроки 1–5 сохранены в закрытом по умолчанию блоке **«1я неделя»**.

Под историей добавлена панель токенов. До запроса агент консервативно оценивает размер выбранного контекста; после успешного ответа показывает точные `prompt_tokens` и `completion_tokens` из `usage` DeepSeek. Там же видны накопленные входные/выходные токены и расчёт ориентировочной стоимости для DeepSeek Flash с учётом cache hit/miss.

Контекст Flash — 1 000 000 токенов. Агент резервирует ещё 512 токенов под ответ: если оценка выбранного контекста и этого резерва превышает окно, API не вызывается, сообщение не попадает в историю и интерфейс предлагает уменьшить `N` или очистить чат. Три отдельные кнопки запускают одинаковую задачу в коротком и длинном контексте и выводят фактический `usage`, стоимость и cache hit/miss; третий сценарий показывает безопасную блокировку до API. У DeepSeek нет параметра выключения кэша: чекбокс создаёт уникальный первый маркер, поэтому запрос не совпадает с уже сохранённым префиксом и не использует кэш.

Браузер отправляет новую реплику, `N` и выбранную стратегию на `POST /api/agent/chat`. Обработчик не принимает историю, системный промпт, `temperature` или `max_tokens`: ими владеет `internal/agent`. Команды checkpoint/веток идут отдельным `PATCH /api/agent/chat` и не вызывают модель.

Для каждого браузерного диалога сервер создаёт `HttpOnly`, `SameSite=Lax` cookie `agent_session`, а для локального пользователя — устойчивый `agent_user`. Поэтому история и рабочая память изолированы по сессиям, а каталог профилей и долгосрочная память общие для сессий одного пользователя.

## Урок 7: сохранение контекста

После каждого успешного ответа агент сохраняет истории всех браузерных сессий в `.local/agent-history.json`. При следующем запуске `go run .` файл загружается до старта HTTP-сервера, поэтому тот же браузер с cookie `agent_session` продолжает предыдущий разговор как после обычной паузы. Системная инструкция отдельно требует от агента учитывать все предыдущие реплики и не отрицать явно сохранённые факты. Локальная папка `.local/` исключена из Git: история остаётся на компьютере и не попадает в коммиты.

Кнопка **«Удалить историю этого чата»** очищает только текущую browser-сессию — сообщения других сессий в файле не затрагиваются. Удаление происходит и из памяти, и из JSON-файла.

Проверка: отправьте агенту сообщение с запоминаемым фактом, остановите сервер через `Ctrl+C`, снова выполните `go run .` и откройте ту же страницу в том же браузере. История должна отобразиться сразу, а в следующем вопросе агент получит и старые реплики, и новую.

## Урок 3: разные способы рассуждения

Вкладка **«3. Разные способы рассуждения»** реализует задание целиком. Введите одну задачу в верхнее поле, не меняйте её и настройки генерации между запусками, затем выберите один режим или нажмите **«Запустить все 4 способа»**.

1. **Прямой ответ** — один API-вызов без специальной инструкции о способе решения. Это базовая точка сравнения.
2. **«Решай пошагово»** — один API-вызов с явной инструкцией дать короткие, проверяемые этапы, вычисления и итог.
3. **Конструктор промпта** — два последовательных API-вызова. Первый, отдельный шаг составляет рабочий промпт для данной задачи при фиксированных `temperature: 0.2` и `max_tokens: 720`. Второй применяет этот промпт к исходной задаче. Для финального решения урока 3 лимит ответа от ползунка снят: сервер использует максимум API `max_tokens: 8192`, чтобы подробная группа экспертов или проверка не обрывались на `finishReason: length`. В карточке результата можно раскрыть «Шаг 1. Промпт, составленный моделью» и увидеть использованную инструкцию.
4. **Группа экспертов** — один API-вызов с группой из аналитика, инженера и критика. Модель обязана выдать подписанные блоки каждого участника, а затем общий вывод. Аналитик формализует условие, инженер предлагает расчёт или алгоритм, критик ищет неверные допущения и ошибки.

Браузер отправляет эти сценарии на отдельный маршрут `POST /api/reasoning`; он не смешивается с режимами контроля ответа из урока 2. Сервер возвращает решение, выбранный подход, безопасную отладочную сводку и — только для третьего подхода — созданный рабочий промпт. Для него также показываются два `finishReason` и число вызовов API.

### Как тестировать задание

Во вкладке есть кнопка **«Подставить тестовую задачу»**. Она вставляет один и тот же аналитический промпт для всех четырёх способов:

```text
Четыре задачи A, B, C и D нужно выполнить в четыре последовательных слота: 1, 2, 3, 4.

Условия:
- A выполняется раньше B;
- C выполняется сразу после A;
- B выполняется сразу перед D.

В каком порядке выполняются задачи? Кратко проверьте, что все условия соблюдены.
```

Эталон, который **не нужно добавлять в запрос**, — `A → C → B → D`. Он показан в интерфейсе только для сверки. После запуска результатов приложение:

- сохраняет отдельную карточку каждого способа, поэтому их можно читать рядом;
- показывает, сколько формулировок текстово различаются;
- отмечает ответы, где явно встречается эталон `A → C → B → D`;
- после четырёх запусков подсказывает, какие варианты совпали с эталоном и по каким критериям выбрать наиболее точный: соблюдены ли все условия, видна ли проверка порядка и нет ли лишних предположений.

Ожидаемый учебный эффект: прямой ответ может быть коротким; вариант «пошагово» легче проверить; созданный промпт обычно делает структуру решения стабильнее; группа экспертов добавляет независимую проверку критиком. Оценку «наиболее точный» приложение делает по фактическому совпадению с эталоном, а при нескольких правильных ответах оставляет итоговый выбор пользователю — по качеству обоснования, а не по длине текста.

Пакетный запуск делает **5 API-вызовов**, потому что третий способ состоит из двух шагов. Он выполняет их последовательно, чтобы результаты было проще сопоставить, и продолжает запуск следующих способов, если один из них вернул ошибку. Для финальных решений всех четырёх способов ограничение длины снято (до технического максимума API `8192` токена); `720` используется только для промежуточного рабочего промпта.

## Урок 4: температура

Вкладка **«4. Температура»** сравнивает ответы на один и тот же запрос при `temperature = 0`, `0.7`, `1.2` и `1.8`. Нажмите **«Подставить пример запроса»** или введите свой текст в верхнее поле, затем выберите **«Запустить 4 сравнения»**.

Приложение делает четыре последовательных запроса на `POST /api/chat`. Во всех четырёх используется одинаковый текст, режим свободного ответа и один и тот же `max_tokens`; меняется только `temperature`. Параметр `top_p` в эксперимент не попадает. Карточки результата сохраняют каждый ответ отдельно и показывают фактическую температуру, лимит токенов, время выполнения и причину остановки модели.

Для удобной проверки встроен пример:

```text
Объясни школьнику в 2–3 предложениях, почему после дождя появляется радуга.
Используй простой русский язык.
```

Сравнивайте ответы по трём критериям:

1. **Точность** — верны ли факты и выполнена ли задача. В примере с радугой ищите капли воды, преломление, внутреннее отражение и разложение света на цвета.
2. **Креативность** — насколько оригинальна, понятна и образна подача, если она не подменяет факты.
3. **Разнообразие** — меняются ли лексика, структура и примеры. Для более честной оценки повторите эксперимент 2–3 раза.

Интерфейс также содержит прозрачные иллюстративные примеры и выводы по применению:

- `temperature = 0` — обычно наиболее стабильная формулировка; подходит для извлечения данных, классификации, инструкций, повторяемых ответов и черновиков кода.
- `temperature = 0.7` — баланс точности и выразительности; подходит для диалогов, объяснений, писем и обычных текстов.
- `temperature = 1.2` — повышенная вариативность; подходит для идей, названий, сторителлинга и поиска множества вариантов, но факты следует отдельно проверить.
- `temperature = 1.8` — максимальная вариативность; подходит для свободного мозгового штурма, художественных образов и необычных концепций. Для фактов, расчётов и точных инструкций используйте только с обязательной проверкой.

Высокая температура не делает ответ неверным сама по себе, а `temperature = 0` не гарантирует истинность. Поэтому приложение показывает фактические результаты запуска и предлагает оценить их по содержанию, а не автоматически объявляет самый длинный или самый необычный текст лучшим.

## Урок 5: версии моделей

Вкладка **«5. Версии моделей»** выполняет один и тот же полный русскоязычный промпт разбора инцидента для `deepseek-flash` и `deepseek-v4-pro`. Промпт зашит на сервере и возвращается в раскрываемом блоке результата, поэтому его нельзя случайно укоротить или изменить в одном из запусков.

Перед запуском backend делает безопасную диагностическую проверку `GET /models` у DeepSeek, а затем читает актуальный каталог OpenRouter по `OPENROUTER_API_KEY`; ключи остаются только в заголовках между backend и провайдерами. Третья карточка появляется только для фактически найденной бесплатной текстовой модели с явным признаком малого размера (1–4B, mini, small или nano) и нулевыми ценами входа и выхода. Если каталог не подтвердил такую модель, приложение не выдумывает идентификатор и не запускает случайную замену.

Для каждого фактически выполненного запуска показываются измеренная сервером длительность, входные/выходные/общие токены из `usage`, причина остановки и расчётная стоимость в USD. Расчёт использует опубликованные peak/off-peak ставки на момент запуска; если API не вернул usage, цена маркируется как неизвестная. При отсутствии отдельных cache-счётчиков входные токены консервативно считаются cache miss — это явно отмечено рядом с цифрой. Блок «Экономика и качество» сопоставляет скорость, токены и цену, но оставляет смысловую оценку человеку по всем десяти обязательным критериям инцидентного разбора.

Источники: [список моделей DeepSeek](https://api-docs.deepseek.com/api/list-models), [модели и тарифы DeepSeek](https://api-docs.deepseek.com/quick_start/pricing), [каталог OpenRouter](https://openrouter.ai/docs/api/api-reference/models/get-models), [бесплатные варианты OpenRouter](https://openrouter.ai/docs/guides/routing/model-variants/free). Цены у провайдеров могут меняться, поэтому подпись результата важнее сохранённого числа из старого запуска.

## Сценарии сравнения ответа

Введите вопрос на странице и используйте его без изменений во всех запусках: так проще сравнить влияние режимов. Переключайте радиокнопки по порядку и делайте по 2–3 запуска в каждом режиме при одинаковых `temperature` или `top_p`.

1. **Без ограничений** — обычный свободный ответ; контроль формата, смысловой длины и окончания отсутствует.
2. **Только формат** — API получает `response_format: {"type":"json_object"}` и инструкцию вернуть только JSON с полями `film`, `actors` и `answer`.
3. **Только длина** — инструкция ограничивает ответ 300 символами, а сервер передаёт `max_tokens: 120`.
4. **Только завершение** — модель получает инструкцию закончить ответ и скрытую стоп-последовательность; она не попадает в видимый ответ.
5. **Все ограничения** — JSON, поле `answer` до 220 символов, инструкция завершить ответ, скрытая стоп-последовательность и лимит `max_tokens: 180`.

В техническом журнале видно выбранный режим, фактический лимит токенов, причину остановки (`finishReason`), переданную стоп-последовательность (`stopSequence`), длительность, число символов и текст, который сервер вернул из модели. Стоп-последовательность видна только в технической сводке, но отсутствует в ответе модели. API-ключ в журнал не попадает.

Страница отправляет `{"prompt":"...","mode":"...","settings":{...}}` на `/api/chat`. Сервер добавляет инструкцию соответствующего режима, вызывает `deepseek-flash` через `https://api.deepseek.com/chat/completions` и возвращает `{"answer":"..."}`.

## Настройки и технический журнал

На странице есть переключатель между двумя режимами сэмплирования и ползунки, которые сразу показывают выбранное значение:

- `temperature` от 0 до 2 — чем выше, тем свободнее и разнообразнее ответ;
- `top_p` от 0 до 1 — выбор из наиболее вероятного «ядра» вариантов;
- `max_tokens` — максимальная длина ответа.

`temperature` и `top_p` не включаются одновременно: DeepSeek рекомендует изменять один из них. `top_k` и `seed` отсутствуют в текущей спецификации Chat Completions, а `frequency_penalty` и `presence_penalty` устарели и не работают — поэтому интерфейс объясняет это, но не отправляет их в API.

Блок «Технический журнал» показывает JSON, который браузер отправил backend, и безопасную сводку ответа: модель, настройки, HTTP-статус, длительность и число символов ответа. Ни API-ключ, ни заголовок `Authorization` журнал никогда не показывает.

В третьем уроке журнал дополнительно показывает маршрут `/api/reasoning`, число выполненных запросов и причины остановки каждого из них. Созданный рабочий промпт не содержит API-ключа и показывается только если включён переключатель в интерфейсе.

## Проверка и troubleshooting

```bash
go test ./...
go vet ./...
node --check static/app.js
```

- **«API-ключ не настроен»** — создайте `.env` по шаблону `.env.example` и укажите в нём `DEEPSEEK_API_KEY`, либо задайте непустую переменную окружения, затем перезапустите `go run .`.
- **«DeepSeek не принял API-ключ»** — проверьте ключ в кабинете DeepSeek, затем экспортируйте его заново и перезапустите сервер.
- **«Не удалось получить ответ»** — проверьте интернет, баланс/лимиты DeepSeek и повторите запрос.
- **Страница не открывается** — убедитесь, что в Terminal написано `listening on http://localhost:8080`, затем откройте именно этот адрес.

## Безопасность

`.gitignore` исключает `.env` и другие локальные файлы с секретами. Не вставляйте ключ в HTML, JavaScript, README, коммиты, скриншоты или сообщения. Сервер не логирует тело запроса, ключ, содержимое `.env` или заголовок `Authorization`.

## Публикация

Перед публикацией проверьте `git status`, чтобы убедиться, что `.env` отсутствует в списке. Публиковать изменения можно только после отдельного подтверждения владельца проекта.
