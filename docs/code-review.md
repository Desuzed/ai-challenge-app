# Автоматическое AI-ревью PR

`cmd/prreview` получает изменения между Git-ревизиями, ищет контекст в документации и коде через существующий RAG и вызывает только DeepSeek Flash (`deepseek-flash`). Другие модели в команде ревью отклоняются. Результат содержит потенциальные баги, архитектурные проблемы и рекомендации. Это отдельная CLI-команда: запуск веб-сервера и история чата не нужны.

## Как работает

1. В GitHub-режиме команда получает метаданные PR через REST API и фиксирует base/head SHA. Локально ревизии задаются флагами.
2. Git вычисляет merge base и three-dot-сравнение: изменения между общим предком и head. Список файлов и diff читаются из локальных Git-объектов, включая удаления и переименования.
3. В отдельном временном каталоге собирается снимок разрешённых tracked-файлов head. Незакоммиченные изменения, `.env`, `.local`, symlink и submodule не читаются в корпус. Код PR не исполняется; checkout, сборка и тесты PR не выполняются.
4. Существующий `ragindex` разбивает документацию и код, включая Go-тесты, на structure-чанки. Быстрый лексический поиск по путям, символам и diff отбирает кандидатов из всего снимка. Для одного изменённого файла эмбеддинги строятся максимум для 8 фрагментов документации и 16 фрагментов кода; общий предел для нескольких файлов — 24/48. Отбор распределяет бюджет между изменёнными файлами и источниками. Затем существующий hybrid retrieval и rerank ищут по этому ограниченному векторному индексу; код вне изменённого файла получает предпочтение.
5. Модель получает цель PR, полный diff файла, старую/новую версии или окна вокруг изменений и до трёх найденных фрагментов из каждого корпуса. Большие версии файлов передаются фрагментами, а не объявляются полными. Контент PR и документация передаются как недоверенные данные в отдельном user message.
6. JSON-ответ проверяется: категория, важность, сценарий, последствия, рекомендация, путь, строка внутри diff и точные цитаты из переданных источников. Разрешены и контекстные строки: при удалении проверки аргумента падающее выражение может оставаться неизменным. Модель получает явные допустимые номера строк обеих сторон. Вывод о баге остаётся логическим выводом модели; совпадение цитаты само по себе его не доказывает.
7. Сохраняются `review.md` и `review.json`. Публикация включается только флагом `-publish`; перед ней повторно проверяются обе ревизии, статус PR и отсутствие draft.

Индекс создаётся заново для фиксированного head и удаляется вместе с временным каталогом. Поэтому новые файлы попадают в discovery, а фрагменты разных веток не смешиваются. Ревью использует только structure-индекс: второй fixed-индекс для него не строится. Постоянного межзапускового cache пока нет. Лог показывает число кандидатов, отобранные фрагменты и прогресс embedding-батчей; отчёт содержит `indexed_chunks` и `candidate_chunks`. Фрагменты вне предварительного отбора не проходят векторный поиск: это явное ограничение полноты, которое позволяет выполнить CI на CPU за разумное время.

## Локальный запуск

Нужны Go 1.25+, Git, запущенная Ollama, `embeddinggemma` и `DEEPSEEK_API_KEY`. Непустое окружение имеет приоритет над локальным `.env`. В CI `.env` не читается. Команда передаёт DeepSeek diff, выбранный код и найденные документы.

```sh
ollama pull embeddinggemma
go run ./cmd/prreview -root . -base main -head HEAD -title 'Описание изменения'
```

Сравниваются только коммиты; незакоммиченные правки не включаются. Если ветка main отсутствует локально, используйте SHA или существующую ветку. Отчёты по умолчанию находятся в `.local/prreview/`.

Для существующего GitHub PR сначала загрузите его Git-объекты, затем запустите:

```sh
git fetch origin
git fetch origin pull/123/head
go run ./cmd/prreview -repo Desuzed/ai-challenge-app -pr 123
```

Замените `123` на номер PR. Метаданные получаются из GitHub, исходники — из локальной базы объектов. Для приватного репозитория задайте `GITHUB_TOKEN` с доступом к содержимому и чтению PR. Для явной публикации добавьте `-publish` и разрешение Pull requests: write. Публикуется review с событием `COMMENT`, без approve/request changes. Повторный review от `github-actions[bot]` для тех же base/head не дублируется; локальная публикация от личного токена этой дедупликацией не охватывается.

Основные флаги: `-output`, `-max-files` (по умолчанию 20), `-model` (допустимо только `deepseek-flash`), `-embedding-model`, `-ollama-url`, `-timeout` (20 минут). `-help` показывает все параметры. В PR-режиме необязательные `-base`/`-head` проверяют ожидаемые SHA события.

## GitHub Actions

Workflow: `.github/workflows/ai-review.yml`. События: opened, synchronize, reopened, ready_for_review. Поддерживаются открытые PR из веток этого же репозитория; draft, forks и Dependabot пропускаются.

Первичная настройка:

1. Добавьте Actions secret `DEEPSEEK_API_KEY` в настройках GitHub-репозитория. Секрет из локального `.env` не переносится автоматически.
2. Проверьте, что Actions разрешены и политика репозитория допускает `contents: read` и `pull-requests: write`.
3. Включите реализацию в базовую ветку. Workflow намеренно собирает ревьювер и зависимости из base SHA, поэтому установочный PR не может провести ревью самого себя: шаг объяснит, что сначала требуется установка в базовую ветку.
4. Откройте следующий PR или добавьте коммит в существующий. Workflow запускает CPU-сервис Ollama 0.12.3, загружает embeddinggemma, строит доверенный бинарник и получает head-объекты без checkout PR.

Результат появляется в GitHub review, сводке запуска Actions и artifact с Markdown/JSON (хранение 7 дней). JSON содержит запросы RAG, пути, SHA, диапазоны строк, chunk IDs, scores и каналы retrieval. Полные тексты найденных чанков в JSON не копируются; цитаты из замечаний сохраняются. Artifact всё равно может содержать выдержки исходного кода: доступ определяется правами GitHub.

Если модель, эмбеддинги, Git или API недоступны либо модель вернула некорректную структуру, запуск завершается ошибкой; чистое ревью не публикуется. При изменении SHA устаревшая публикация отклоняется. Уже начавшийся review привязан к конкретному commit_id; GitHub не предоставляет здесь атомарного compare-and-publish. Concurrency отменяет предыдущий запуск для PR.

## Покрытие и ограничения

Корпус включает Markdown, Go (включая тесты), JS/TS/JSX/TSX, CSS, HTML, `go.mod`, текстовые/JSON/YAML-файлы из docs и конфигурацию `.github/workflows`. Исключаются скрытые файлы за пределами `.github`, vendor/node_modules/dist/build, reports/fixtures/testdata/secrets, типовые generated/minified-файлы и файлы с заголовком Code generated / DO NOT EDIT. Это allowlist, а не универсальный детектор секретов: не коммитьте секреты в исходники.

Лимиты MVP: 160 KiB на файл корпуса, 300 файлов / 3 MiB на корпус, 32 KiB diff на файл, 20 проверяемых файлов (настраивается 1–100), 90000 Unicode-символов входа на вызов модели и максимум 5 замечаний на файл. Размер входа измеряется символами, не точным tokenizer. Пропущенные файлы и нехватка RAG-контекста отражаются в отчёте; большие PR могут быть проверены частично. Для больших файлов окна вокруг изменений ограничены 16000 символов на версию.

Пустые разделы означают отсутствие сформированных замечаний в просмотренном контексте. Нет гарантии обнаружения всех дефектов. В MVP нет call graph/AST-анализа, исполнения тестов PR, inline comments и отдельного LLM-verifier. Перенос в vector DB для этого объёма не требуется.

## Проверка

```sh
go test ./internal/prreview ./internal/githubpr ./cmd/prreview
go test ./...
go vet ./...
git diff --check
```

Тесты создают настоящие временные Git-репозитории и проверяют снимок SHA, merge base, dirty working tree, переименования/удаления, исключение symlink/секретов, docs+code retrieval, отказ при ошибках и выдуманных цитатах. GitHub-тесты подменяют HTTP transport: проверяют COMMENT, SHA, дедупликацию и запрет устаревшей публикации. Эмбеддинги и ответы LLM в unit-тестах подставные.

Живая демонстрация с настоящими embeddings и DeepSeek:

```sh
python3 scripts/demo_pr_review.py
```

Скрипт создаёт отдельный маленький Git-репозиторий в `.local/prreview-demo/run-*`, документацию контракта, Go-код и тест вызывающего кода. Проверяет удаление защиты пустого среза и корректный рефакторинг. `summary.json` содержит результат: найден дефект в buggy-сценарии, нет дефектов в clean-сценарии, в обоих случаях retrieval использовал документацию и код. При невыполнении ожиданий скрипт возвращает ненулевой статус; это оценка конкретных примеров, не универсальная метрика качества. В DeepSeek передаётся только сгенерированный пример; ключ читается из окружения или `.env` проекта, не копируется в пример и не выводится. Публикация GitHub не выполняется.
