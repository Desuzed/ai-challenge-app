# Факты проекта для RAG-чата

## Локальный запуск и ключ

Это локальный Go web-сервис. Для сборки требуется Go 1.25 или новее. Из корня проекта сервер запускается командой `go run .` и по умолчанию слушает `http://localhost:8080`; порт задаётся переменной `PORT`.

Для локальной конфигурации скопируйте шаблон командой `cp .env.example .env` и укажите `DEEPSEEK_API_KEY`. Непустая переменная окружения процесса имеет приоритет над значением из `.env`. Ключ читает сервер и отправляет DeepSeek только в HTTP-заголовке `Authorization`; браузер его не получает. Не добавляйте `.env` в Git. Шаблон `.env.example` не содержит рабочего ключа.

Обычный чат принимает сообщения через `POST /api/agent/chat`. Там же доступны GET для состояния/истории, PATCH для параметров и команд контекста и DELETE для очистки истории. История браузерной сессии хранится в `.local/agent-history.json`. В обычном режиме полная история остаётся в архиве; sliding window отправляет модели только последние N сообщений. Настройка N допустима от 2 до 40, новый чат по умолчанию использует 32. Для 15 обменов поместите 30 реплик в окно; при меньшем N явная память задачи сохраняет исходную цель и уточнения.

## Поиск по документам

RAG включается параметром **«Поиск по документам (RAG)»** существующего чата. При включённом поиске новый вопрос проходит через тот же обычный чат и его выбранные модель, стратегию, профиль, память, planner и MCP-инструменты. Поиск использует текущий вопрос; цель и термины задачи могут помогать отдельным запросом при коротких анафорических уточнениях. Контекст к LLM по-прежнему строится текущей стратегией: sliding window отправляет последние N user/assistant сообщений, Facts добавляет sticky facts, а Branching использует активную ветку.

Для локального поиска нужны Ollama по адресу `OLLAMA_URL` (по умолчанию `http://127.0.0.1:11434`) и embedding-модель `embeddinggemma`. Список индексируемых файлов задаётся в `internal/ragindex.DefaultFiles`. Пересоберите индексы командой `go run ./cmd/indexdocs`; они находятся в `.local/rag`.

Индексатор строит два вида фрагментов. Стратегия `fixed` делит текст на окна по 1200 Unicode-символов с перекрытием 150 символов. Стратегия `structure` сначала делит Markdown по заголовкам, Go-файлы — по объявлениям типов и функций, а длинные разделы затем делит теми же окнами. Фрагмент хранит путь источника, заголовок, раздел, chunk ID, исходный текст и embedding.

Поиск ставит текущий вопрос первым; цель и термины задачи идут отдельным supplemental-запросом только для коротких анафорических уточнений. По умолчанию vector-канал берёт 8 кандидатов и применяет к ним cosine-порог 0.35. Отдельный lexical-канал просматривает корпус и допускает кандидатов при совпадении минимум двух разных содержательных терминов; числа не засчитываются как термины. Каналы объединяются до финального top-K=3, поэтому lexical-кандидат может быть передан модели даже при cosine ниже порога. Trace различает каналы, показывает исходный cosine и lexical gate. `window/окно` истории не смешивается с `chunk/фрагментом` индекса. Rewrite — локальный детерминированный heuristic; rerank остаётся необязательным вторым этапом после fusion: `0.8 × cosine + 0.2 × lexical coverage` для vector/hybrid candidates, lexical-only ранжируются по lexical signal. UI позволяет менять top-K, cosine-порог, rewrite и rerank.

Для обычных RAG-ответов сервер просит API вернуть JSON (`response_format: json_object`) с answer и claims; обычный резерв ответа — 2200 токенов. При явной просьбе о подробном ответе в текущем ходе он повышается до 6400, даже если раньше пользователь предпочитал краткий стиль. Парсер принимает один полный JSON-root: bare, в Markdown code fence или окружённый короткой прозой. Он не восстанавливает вложенный объект из обрезанного ответа и отвергает несколько конкурирующих envelopes. Документальные claims отдельно проверяются: chunk должен быть среди результатов поиска, а цитата должна дословно входить в его текст. Ответ о фактах проекта строится из проверенных claims; блок «Источники» содержит файл, раздел, ID и цитату. Отсутствие подходящих документов, неподдерживаемый формат ответа и обрезание по лимиту имеют разные причины и не маскируются друг под друга. RAG trace показывает режим structured output, output-token budget, provider finish reason и длину ответа; сырое содержимое completion не сохраняется в trace. Буквальное совпадение цитаты не гарантирует, что она по смыслу доказывает claim; семантическая связь требует отдельной проверки.

Источники MCP показываются отдельно и маркируются как результат соответствующего инструмента. Они не выдаются за цитаты из индексируемых документов. Ответы обычного provider path запрашиваются в JSON-режиме; tool-calling flow сохраняет выбранные MCP-инструменты и отдельно показывает их provenance. При паузе задачи поиск можно выполнить, но модель и инструменты не запускаются, план не продвигается, а ответ явно говорит, что документальные доказательства не использовались.

## Путь вопроса: поиск, память, проверка цитат и сохранение истории

Сервер определяет сессию, обновляет TaskMemory из явных пользовательских уточнений и ищет документы по текущему вопросу; цель и термины идут отдельным поиском только для короткой анафоры. Перед вызовом модели сервер добавляет новую реплику в активный диалог. Vector candidates проходят cosine-порог, отдельный lexical scan требует два разных содержательных термина, затем каналы объединяются до top-K. В запрос модели попадают найденные фрагменты и контекст выбранной стратегии. Ответ приходит как JSON claims; сервер принимает claim, только если указан найденный chunk и цитата дословно есть в его тексте. Фактическое объяснение строится из принятых claims, источники содержат путь, раздел, chunk ID и цитату; TaskMemory показывается отдельно как данные пользователя. Явная подробная просьба текущего хода важнее прежнего краткого стиля и поднимает резерв ответа с 2200 до 6400 токенов. Реплики, ответ и TaskMemory сохраняются в `.local/agent-history.json`; полный архив не обрезается, а sliding window отправляет модели последние N сообщений.

## Память задачи

TaskMemory хранится отдельно от планировщика (`TaskState`) и обновляется только пользовательскими сообщениями. Сохраняются явная цель, уточнения, актуальные ограничения и термины, их пользовательская цитата и номер хода. Если в первой реплике нет поля `Цель:`, исходная реплика используется как буквальный fallback цели.

Поддерживаются префиксы `Цель:`, `Уточнение:`, `Ограничения:`, `Термины:`, `Термин:`, `Отменить ограничение:` и `Ограничение больше не действует:`. Каждое поле задаётся на отдельной строке; несколько значений можно разделять точкой с запятой. Новое поле `Ограничения:` заменяет предыдущий список. Повторный `Термин:` с тем же именем заменяет его старое значение. Указание отмены удаляет совпадающее ограничение. Вопросы сами по себе не записываются как факты пользователя.

Текущая TaskMemory имеет приоритет над противоречащими ей историческими sticky facts, сохранёнными предпочтениями профиля, рабочей/долговременной памятью и старой спецификацией planner для того же пользовательского ограничения или термина. Это не меняет выбранную стратегию, профиль, модель или другие настройки. Task/state/global invariants остаются обязательными; если пользовательское ограничение конфликтует с таким правилом, ассистент должен назвать конфликт и предложить совместимый вариант. TaskMemory — данные пользователя, не доказательства о приложении: ответы о проекте всё равно требуют проверенных документов или помеченного результата MCP.

При очистке переписки цель и память задачи сбрасываются, а параметры чата — стратегия, N, модель, активный профиль и режим planner — сохраняются. В Branching память восстанавливается из пользовательских реплик активной ветки. Старые данные отдельного mini-chat мигрируют в обычную историю, если обычная история пуста; при наличии обычной истории прежние данные остаются сохранённым legacy-архивом.
