# Проверка общего чата с RAG и памятью задачи

Дата: 5 октября 2026 года.

## Что проверяем

Один существующий чат и маршрут `/api/agent/chat` используют историю,
выбранную стратегию контекста, профиль, Sticky Facts, рабочую и долгосрочную
память, глобальные инварианты и планировщик. RAG добавляет поиск и проверку
документальных цитат к тому же контексту. Отдельного режима мини-чата нет.

Для новых сессий окно по умолчанию — 32 сообщения. Сохранённые значения N и
выбранные стратегии не меняются автоматически. Окно ограничивает запрос к
модели, а не сохранённую историю. Память задачи хранит цель, уточнения,
актуальные ограничения и термины с указанием пользовательского хода.

## Локальные проверки

- Весь набор `go test -race ./...` прошёл, включая прежние задания.
- `go vet ./...` прошёл без замечаний.
- `node --check static/app.js` прошёл без ошибок синтаксиса.
- `git diff --check` прошёл без ошибок оформления.
- После исправлений разбора ответа и поиска повторно прошёл весь набор
  `go test -race ./...`, включая HTTP-тест запроса JSON-формата к провайдеру.

Проверки покрывают сохранение истории и памяти после перезапуска, замену
ограничений и терминов, возврат в ветки и переходы стратегий, перенос прежнего
mini-chat состояния без потери уже существующей обычной истории, сброс задачи
с сохранением параметров, профиль/Sticky Facts/инварианты и планировщик.
Проверяются пауза до вызова модели и остановка запроса в процессе работы;
при RAG сохраняются честные источники и след выполненного поиска.

Вопросы о метаданных фрагментов и учебном видео не запускают MCP. Явные
запросы о видеофайлах, загрузке и погоде продолжают использовать инструменты.
Документальные ответы не выводят свободный непроверенный текст модели в обход
проверки claims. Планировщик может предлагать план по пользовательской цели
с пустыми документальными источниками; этапы меняет сервер по подтверждению
пользователя.

## Отказ при разборе ответа модели

Ручная проверка пользователя обнаружила отказ на вопрос «Чем сохранённая
история отличается от сообщений, отправляемых модели в текущем запросе?».
Прежний текст отказа означал ошибку разбора JSON до проверки цитат. Сырой
ответ той попытки не сохранялся, поэтому его точная форма неизвестна.

Обычные документальные RAG-запросы теперь включают `response_format:
{"type":"json_object"}` в запросе к DeepSeek. Обычный RAG-лимит 2200 и planner-лимит 3200 сохранены;
явная подробная просьба текущего хода использует резерв 6400 токенов. Вызовы с MCP продолжают использовать прежний механизм
инструментов. Разбор принимает один полный JSON-объект, в том числе внутри
Markdown-блока или окружённый пояснением; окружающий текст не выводится.
Обрезанный внешний объект не восстанавливается из вложенных объектов,
несколько объектов отвергаются. Цитаты проверяются как прежде.

Офлайн-регрессия использует тот же пользовательский вопрос с отключёнными
rewrite/rerank и проверяет обычный JSON, Markdown-обёртку, пояснение вокруг
JSON, обрезанный ответ и неоднозначные объекты. Отдельно проверено применение
плана только из того же проверенного JSON без перехода фазы по решению модели.
В техническом журнале доступны причина отказа, `finish_reason`, число символов
ответа, лимит токенов и признак использования JSON-формата API. Ошибка формата
и обрезанный ответ больше не описываются как незнание ответа на вопрос.

## Поиск размера фрагментов

Следующая ручная проверка обнаружила отказ на вопрос «Какой размер
фиксированных фрагментов и их перекрытие?». Локальная диагностика с настоящей
Ollama и прежним индексом воспроизвела ошибку поиска: при всех четырёх
сочетаниях rewrite/rerank запрос с сохранённой памятью выбирал документы о
памяти диалога, а фрагменты с ответом 1200/150 не попадали в финальную тройку.
Проверка без добавления цели тоже показала слабые векторные совпадения.

Теперь конкретный вопрос ищется отдельно от общей цели. Для коротких явных
анафорических уточнений память используется дополнительным запросом, а в
контексте ответа модели память задачи сохраняется на каждом ходе. Поиск
объединяет векторный канал и отдельный лексический канал по всему корпусу.
Порог cosine применяется к векторному каналу; лексический канал требует
совпадения минимум двух значимых понятий, а совпадение трёх даёт ему приоритет
при объединении кандидатов. Число само по себе не считается совпадением
понятия. Окно истории и индексируемый фрагмент — разные понятия.

Офлайн-тест проверяет исходный вопрос с намеренно неверным векторным лидером:
правильный фрагмент сохраняется в финальных top-1 и top-3. Отдельные проверки
покрывают вопрос о колесе, один термин вместе с числом и отличие Sliding
Window от fixed chunk. Канал кандидата, настоящий cosine и условия
лексического допуска видны в технических данных; проверка цитат сохранена.
В журнале также различаются пустая выдача, отсутствие claims в ответе модели
и неверные доказательства; число предложенных и проверенных claims явно
показывается, включая нулевые значения.

После пересборки индекса проверен настоящий `rag.Searcher` с локальной
Ollama: исходный вопрос и две переформулировки, каждое сочетание rewrite/rerank.
Во всех 12 проверках фрагмент с 1200 и 150 находился на первом месте. Это
проверка поиска, без генерации ответа DeepSeek. Дополнительно прочитаны
результаты поиска по вопросам об истории, HTTP-маршруте и метаданных.

## Подробное итоговое объяснение и состояние сессий

Пользовательский вопрос «Подготовь итоговое объяснение для моего видео: путь
вопроса, поиск, память, проверка цитат и сохранение истории. Учти актуальную
просьбу о подробном ответе и приложи источники.» выявил две проблемы: лимит
JSON-ответа 2200 токенов и поиск внутренних предикатов по словам оформления.
Теперь поисковый запрос отделяет тему от просьб о видео, стиле и источниках.
Документация содержит цельное описание пути вопроса. Подробный ответ получает
резерв 6400, а новая просьба о подробности имеет приоритет над прежней краткостью
для текущего ответа. Этот резерв согласован между проверкой контекста, запросом
провайдеру и trace. Вывод состоит только из проверенных claims в связном порядке;
свободное поле answer не обходит проверку источников.

После пересборки индекса настоящий поиск с локальной Ollama поставил цельный
раздел о пути вопроса первым для очищенной тематической формулировки при всех
четырёх сочетаниях rewrite/rerank. Тест подтверждает, что точная пользовательская
реплика преобразуется в эту формулировку в реальном обработчике. Прямой поиск
по неочищенной реплике всё ещё предпочитает функцию с совпадающими словами;
поэтому проверяются обе формулировки. Ранее исправленные три вопроса о размере
фрагментов сохранили ответ 1200/150 на первом месте во всех 12 проверках.
Это проверка retrieval, а не настоящий ответ DeepSeek.

Локальные тесты проверили точную поисковую формулировку, приоритет текущей
подробной просьбы при сохранённом кратком ограничении, одинаковый резерв в
request/report/trace, вывод проверенного текста и исключение непроверенного
answer. Весь набор тестов с race detector и статические проверки прошли.

Чтение сохранённого состояния подтвердило два разных диалога одного пользователя:
старый содержит 34 сообщения, N=4 и прежние цель, уточнение, ограничения и термин;
новый содержит 4 сообщения, N=32 и цель из первого нового вопроса, без прежних
уточнений, ограничений и терминов. Старые данные не удалены. Cookie agent_session
действует 24 часа и не продлевается при чтении, agent_user — 365 дней. По JSON
нельзя установить точную причину смены cookie. Очистка и объединение сессий при
диагностике не выполнялись.

## Сохранение N без сообщения модели

Исправлено перезаписывание введённого N старым GET-ответом каждые 15 секунд.
До исправления поле только проверялось, а значение сохранялось при следующем
POST сообщения. Теперь валидный ввод сохраняется отдельной командой PATCH
`set_recent_messages`, изменения сериализованы, а версии редактирования и
подтверждённого состояния защищают поле от старых GET/PATCH-ответов. Перед
POST выполняется сохранение актуального N.

HTTP-регрессия проверила GET32 → PATCH4 → GET4, отклонение N=1 без смены
сохранённого N и GET4 после нового запуска persistent-agent. Node VM-диагностика
на актуальных функциях интерфейса проверила старый GET после подтверждения N=4,
запоздалый ответ другой PATCH-команды и быстрые изменения 4→6. Полный набор
race-тестов, vet, синтаксис JavaScript и diff-check прошли.

В браузере изменено N с 10 на 4 без сообщения модели: после более чем 15 секунд
автообновления и перезагрузки страницы осталось 4. Сохранённые messages,
TaskMemory и пользовательские записи сравнили с резервной копией: они не
изменились. Оба индекса обновлены после правок, контрольные суммы актуальны.

## Индекс и интерфейс

Оба индекса пересобраны через настоящую локальную Ollama с `embeddinggemma`.
Индексируются 9 файлов: 278 фиксированных и 467 структурных фрагментов.
Все векторы имеют 768 элементов, пустых векторов нет. SHA-256 каждого
индексированного файла совпадает с окончательными исходниками; `.env` и
пользовательская история не входят в корпус.

Обновлённое приложение запущено на <http://localhost:8080>. Интерфейс проверен:
один чат, прежние параметры доступны, панель памяти задачи видна, RAG включён,
ошибок JavaScript в консоли нет. Сохранённое N=10 браузерной сессии осталось
прежним; значение 32 используется по умолчанию для новых сессий. Сообщения
модели из интерфейса при проверке не отправлялись.

Дополнительные регрессионные тесты проверяют разбор структурированных ответов
при MCP+RAG и отдельные источники документов и инструментов. Серверные
подтверждения успешных MCP-команд не отвергаются как неверный JSON;
ответ провайдера не может выдать себя за серверное подтверждение.

## Длинные офлайн-сценарии

| Сценарий | Пользовательские ходы | Сохранённые реплики | Окно |
|---|---:|---:|---:|
| Подготовка инструкции запуска | 15 | 30 | 4 сообщения |
| Объяснение архитектуры RAG и памяти | 15 | 30 | 4 сообщения |

Используется настоящий `rag.Searcher` с тестовым индексом. Эмбеддинги и
ответы модели заменены контролируемыми тестовыми реализациями. Вопросы внутри
тестов служат проверке состояния; это не запись настоящих ответов на все
вопросы из видеосценариев. Проверяется сохранение памяти и источников, а
качество настоящих ответов DeepSeek оценивается отдельно.

## Живые сценарии

По просьбе пользователя живой прогон не выполнялся. Подготовлены
[два сценария для видео](rag-task-chat-demo.md), по 15 вопросов в каждом.
Они выполняются последовательно в существующем чате с включённым RAG.
Между сценариями нужно очистить историю.

Дополнительно подготовлена команда для самостоятельного автоматического
прогона:

```sh
go run ./cmd/evaluateragchat -root . -window 4
```

Она использует настоящие Ollama и DeepSeek и сохраняет результаты после
каждого хода в `.local/rag-chat-eval/results.json` и `results.md`. История
проверки хранится отдельно от пользовательской.

Дословное совпадение цитаты с документом подтверждает наличие цитаты в
найденном фрагменте. Оно не доказывает смысловую поддержку утверждения —
эту связь и соблюдение пожеланий в итоговом ответе нужно оценить по настоящим
ответам.
