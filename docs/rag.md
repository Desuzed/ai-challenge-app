# Поиск по документации (RAG)

## Разделение задач

RAG сначала ищет подходящие документы, затем передаёт найденные фрагменты модели ответа. Эмбеддинг нужен для поиска смысловой близости, а генеративная модель — для объяснения. Поиск не обучает модель заново и не гарантирует правильный ответ без проверки источников.

В обычном чате поиск включается `ragEnabled`. `/help <вопрос>` и `/structure` выполняют поиск независимо от переключателя только для текущего вызова. `/help` без вопроса показывает инструкцию; эта команда и `/reindex` не вызывают генеративную модель. История, стратегия, профиль и пользовательская память продолжают применяться. `/help` ограничивает поиск текстовой документацией; обычный RAG также может выбирать индексированные Go-исходники.

## Корпус

По умолчанию `ragindex.DefaultSources` собирает README, рекурсивно все `.md`, `.txt`, `.json`, `.yaml`, `.yml` из `docs` и явно выбранные Go-файлы из `DefaultFiles`. В корпус включены основные компоненты агента, HTTP-обработчики, модели данных и Project MCP. Тесты, `.env`, `.local`, отчёты и benchmark fixtures туда не входят. Символические ссылки в документации отклоняются.

Можно переопределить набор относительных UTF-8 путей:

```sh
go run ./cmd/indexdocs -root . -files README.md,docs/architecture.md,docs/api.md
```

Индексатор поддерживает `-root`, `-output`, `-model`, `-ollama-url` и `-files`. Приложение использует индекс `.local/rag/index-structure.json` с моделью `embeddinggemma`; пользовательский индекс/модель требуют согласованной настройки поискового слоя.

## Фрагменты и актуальность

Fixed делит текст на окна по 1200 Unicode-символов с перекрытием 150. Structure сначала делит Markdown по заголовкам и Go по объявлениям, объединяет слишком короткие разделы, затем делит длинные. Для JSON и YAML используется оконное разбиение текста без разбора OpenAPI или AST.

Чанк хранит `source`, `title`, `section`, `chunk_id`, `text`, `embedding`. Метаданные файла содержат SHA-256. Два индекса и отчёт сохраняются в `.local/rag/`: `index-fixed.json`, `index-structure.json`, `report.json`.

```sh
go run ./cmd/indexdocs -root .
```

Индексатор переиспользует эмбеддинги неизменившегося текста. Подключение к Ollama должно быть настоящим: при ошибке векторы не подменяются. Поиск проверяет хеши включённых файлов и отклоняет устаревший индекс. Добавление нового файла не обновляет индекс автоматически: после любого изменения корпуса запустите индексатор.

## Поиск и ранжирование

Текущий вопрос — основной запрос. Цель и термины TaskMemory могут использоваться отдельно для коротких анафорических уточнений. Локальный heuristic rewrite добавляет поисковые термины; это не вызов отдельной LLM.

По умолчанию vector search получает 8 кандидатов, применяет cosine-порог 0.35. Lexical scan допускает кандидата при совпадении как минимум двух разных содержательных терминов; числа сами по себе не засчитываются. Каналы объединяются до финальных 3 фрагментов. Поэтому lexical-кандидат может попасть в контекст при cosine ниже порога.

Необязательный rerank использует `0.8 × cosine + 0.2 × lexical coverage` для vector/hybrid кандидатов; lexical-only ранжируются по lexical signal. Порог, количество кандидатов, rewrite и rerank доступны в параметрах. Rerank не возвращает фрагменты, уже потерянные на этапе фильтрации.

## Ответ и цитаты

Обзорные команды вроде `/help расскажи о проекте` выбирают до двух первых фрагментов индексированного README. Этот канал помечен `candidateSource: "overview"`: он не зависит от cosine-порога общего вопроса. SHA-256, ID чанка и точные цитаты проверяются как обычно; score остаётся фактическим cosine. Для конкретных вопросов и неизвестных тем этот канал не включается. Если README отсутствует в корпусе, применяется обычный поиск.

Модель получает найденные чанки и возвращает один полный JSON-envelope с claims. Claim содержит утверждение и evidence: ID найденного чанка и точную цитату. Парсер допускает JSON в code fence или короткой обёртке, но отвергает обрезанный корень и конкурирующие envelopes.

Сервер принимает доказательство только из финально найденного чанка и только при дословном совпадении цитаты. Факты проекта выводятся из проверенных claims, а не из непроверенного текста `answer`. В ответе видны файл, раздел, ID и цитата. Результаты MCP маркируются отдельно и не выдаются за документы.

Обычный резерв ответа RAG — 2200 токенов; явная подробная просьба текущего хода может поднять его до 6400. Trace показывает фактический бюджет и причину остановки. Отсутствие retrieval, неверный JSON, неверная evidence и отсутствие claims различаются. Если фрагментов нет, обычный документальный ответ пропускает вызов генеративной модели. Для команд помощи при неверном JSON, неподтверждённых цитатах или пустых claims допускается одна повторная генерация, включая API-провайдера. Сохранённые настройки пользователя не меняются; фактический бюджет и расход обеих попыток отражены в trace и usage. Для компактного локального RAG провайдер может увеличить бюджет повторной попытки до 2200, как описано в разделе моделей. `/help` и `/structure` не читают текущее состояние Git. Команда `/diff` получает ветку через MCP без RAG и вызова генеративной модели.

Точная цитата подтверждает наличие текста в источнике. Она не доказывает, что утверждение логически следует из цитаты; эту связь оценивают отдельно. Для диагностики доступны `ragTrace`, `ragSources`, `ragAbstained`, `ragReason`, `ragModelCallSkipped`.

Для `/help` поиск ограничен 30 секундами. В основном чате общий предел запроса DeepSeek — 60 секунд, включая поиск и обе возможные генерации. При бюджете до 768 токенов контракт помощи ограничивает ответ одним коротким claim с одной цитатой, не изменяя сохранённый `maxTokens`.
